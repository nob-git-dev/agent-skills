# 設計後の確認と引き継ぎ

## 目的に合う確認を選ぶ

検証の項目と合格条件は対象の利用者・環境・要件に合わせる。原稿にない一律の秒数、ピクセル値、成功率を事実として設定しない。以下はスキル編者が用意した確認観点で、実測結果ではない。

| 課題 | 確認すること | 関連カード |
|---|---|---|
| 主要導線 | 最初にする操作が見つかり、目的へ到達する。不要な副作用を起こさない | P-V06、P-I07 |
| 世界観 | 意図した印象を保ち、主要な操作や必要な情報を妨げない | P-V01、P-V03 |
| 情報の整理 | 目的の項目を探せる。分類の変更や低頻度項目でも迷わない | P-V02、P-V05 |
| 多言語 | 実際の文言、長い翻訳、文字サイズ変更、小型画面で確認する | P-V04、P-V07 |
| 動的表示 | 重なりや表示切替で対象・状態を見失わない。結果が分かる | P-V08 |
| 読み込み | 高速・低速・失敗の状態を区別し、完了後に余計な待ちが残らない | P-I01 |
| 時間の主導権 | スキップ、一時停止、再開、セリフ送りが意図どおりに働く | P-I02〜P-I04 |
| 入力設定 | 通常操作と再割当を区別し、取消・退出・復帰ができる | P-I05、P-A06 |
| 利用者切替 | その人の設定が適用され、共有環境で別人へ誤適用しない | P-I06 |
| 言葉 | 項目名を知らない人にも、何ができるかを説明する | P-I08 |
| 支援 | 別の情報経路や調整を使っても、主要タスクへ到達できる | P-A01〜P-A07 |

## 確認の種類を区別する

1. **静的確認**：文言、画面、コード、仕様を読んだ。
2. **操作確認**：実際に操作して遷移・状態・復帰を確かめた。
3. **対象利用者による確認**：想定する利用者や支援を必要とする人と確かめた。

できていない種類を「済み」にしない。画像だけでは操作や読み上げを検証できない。コードの存在だけでは使いやすさを証明できない。対応規格の審査・適合確認が必要な案件は別の要件・手順と組み合わせる。

## 設計・レビューの記録

案件の規模に合わせ、以下の情報を短く残す。

- 対象、目的、利用者、端末・入力・言語、固定要件
- 観測した問題と、推測に留まる原因
- 採用したP-*とE-*、採用理由、今回に合わせた変更
- 見送った候補と、条件が合わない理由（重要なものだけ）
- 具体的な画面・文言・遷移・設定の案
- 確認結果：確認済み／未確認／対象外、実施した確認の種類
- 残る不確実性、次に確かめること

小さな修正では数行でよい。原稿の解説を長く引用することが目的ではない。

## 実装担当へ渡す

実装も依頼されているときは、採用した案、必要な状態と入力、例外・復帰、受け入れ条件を渡す。React等ならリポジトリのuiスキルを任意で利用できる。このスキルは特定フレームワークやプラグインを要求しない。

既存UIの基準と衝突する場合は、案件の固定要件を先に確認する。例えば「ローディングを必ず伝える」と「演出に溶け込ませる」は、利用者に処理中と分かるかで調整できる。未確定の優先順位だけが結果を変える場合に確認し、形式的な追加承認を増やさない。
