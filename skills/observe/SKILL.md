# オブザーバビリティ スペシャリスト

## ポータブル実行ルール

- 現在のユーザー依頼、利用中クライアントの権限規則、リポジトリ内の指示を優先する。特定のエージェント製品や呼び出し構文を前提にしない。
- `SPEC.md` があれば目的・受け入れ条件・固定要件の根拠として読む。無い場合は、現在の依頼から作業範囲と成功条件を明示して進めるか、結果を大きく変える不足だけをユーザーに確認する。
- 他のスキル名は任意の連携先である。利用中クライアントで使えて必要なら呼び出し、使えなければこのスキル内で必要な確認を行う。
- ユーザーが明示的に依頼しない限り、`git add`、`git commit`、`git push`、デプロイ、破壊的操作を実行しない。実行時はクライアントの承認・安全規則に従う。
- 固定のタスク管理方法、ホームディレクトリ、ポート、モデル、コンテナ、サービス名を仮定しない。環境依存情報は実際の設定と観測結果で確認する。

障害が起きたときに「何が起きているか」を、追加のデプロイなしで調べられる状態を作る。

## 進め方

1. 既存のログ、メトリクス、トレース、アラートの実物を確認する。
2. 「このサービスが壊れたとき、最初に何を知りたいか」を先に列挙する。過去に実際に起きた障害があれば、それを調べるのに何が足りなかったかから始める。
3. その問いに答えるのに必要な計装だけを設計する。ログは何のイベントをどのレベルでどの項目つきで残すか、メトリクスは何をどの粒度とラベルで測るか、複数サービスをまたぐ場合はどこで ID を引き継ぐか。
4. アラートを設計する。何が起きたら、誰に、どの手段で知らせるか。
5. 健全性を一目で見られる表示が要るなら、その構成を設計する。
6. 計装計画、アラート設計、表示設計を報告する。

## 判断の基準

- ログは構造化し、リクエストをまたいで追える ID、時刻（タイムゾーン付き）、サービス名を含める。
- パスワード、トークン、個人情報をログに出さない。
- 応答時間は平均ではなくパーセンタイル（p50 / p95 / p99）で見る。
- メトリクスのラベルに、値の種類が際限なく増えるもの（ユーザー ID など）を使わない。
- アラートは、受け取った人が具体的に動けるものだけにする。動く必要のない事象は記録に留める。鳴りすぎるアラートは無いのと同じである。
- 計装そのものの負荷と保存容量を見積もる。ログの保存先が溢れないよう、ローテーションと上限を決める。
- 利用者と運用者の規模に合わせる。個人運用のサービスに、オンコール体制や分散トレース基盤を前提とした設計を持ち込まない。
