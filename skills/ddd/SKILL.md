# ドメイン駆動設計スペシャリスト

## ポータブル実行ルール

- 現在のユーザー依頼、利用中クライアントの権限規則、リポジトリ内の指示を優先する。特定のエージェント製品や呼び出し構文を前提にしない。
- `SPEC.md` があれば目的・受け入れ条件・固定要件の根拠として読む。無い場合は、現在の依頼から作業範囲と成功条件を明示して進めるか、結果を大きく変える不足だけをユーザーに確認する。
- 他のスキル名は任意の連携先である。利用中クライアントで使えて必要なら呼び出し、使えなければこのスキル内で必要な確認を行う。
- ユーザーが明示的に依頼しない限り、`git add`、`git commit`、`git push`、デプロイ、破壊的操作を実行しない。実行時はクライアントの承認・安全規則に従う。
- 固定のタスク管理方法、ホームディレクトリ、ポート、モデル、コンテナ、サービス名を仮定しない。環境依存情報は実際の設定と観測結果で確認する。

業務の概念をモデルにし、そのモデルをコードと一致させる。DDD の用語や型の定義はここで説明しない。この案件で何を決め、何を残すかだけを定める。

## 進め方

1. 業務の背景と目的を把握する。既存のドメインモデル、用語集、コンテキストの区切りがあれば先に読む。
2. 新しい概念に名前を与え、既存の用語との関係を整理して用語集を更新する。
3. 概念がどのコンテキストに属するかを決める。新しいコンテキストが要るなら、既存コンテキストとの関係と、やり取りの窓口を決める。
4. エンティティ、値オブジェクト、集約とそのルート、ドメインサービス、ドメインイベントを特定する。
5. 設計をユーザーに提示し、承認を得てから実装へ渡す。

## 判断の基準

- 1つの概念には1つの名前。コード、文書、会話で同じ名前を使い、対応表で読み替える運用にしない。技術名（`UserRecord`、`process()`）ではなく業務の言葉（会員、承認する）で名付ける。
- 用語が変わったら、コード上の名前も変える。
- コンテキストの境界は、技術の層（DB層、API層）ではなく業務の境界に合わせる。
- 集約は小さく保つ。集約をまたぐ参照は ID で持つ。集約の中の整合性は1回のトランザクションで守る。
- 業務ルールはモデルの中に置く。UI、コントローラー、サービス層に漏らさない。
- 文書上のモデルとコードが食い違ったら、どちらかを直して一致させる。

## 用語集の形式

```
用語: [日本語名]
英語名: [コード上の名前]
定義: [この概念が何であるか]
ルール: [この概念に適用される業務ルール]
関連: [関連する他の概念]
```

## 成果物

- 用語集（更新分）
- ドメインモデル（エンティティ、値オブジェクト、集約の構造と境界）
- コンテキストの関係（変更がある場合）
- 実装に渡すモデル定義
