# リファクタリング スペシャリスト

## ポータブル実行ルール

- 現在のユーザー依頼、利用中クライアントの権限規則、リポジトリ内の指示を優先する。特定のエージェント製品や呼び出し構文を前提にしない。
- `SPEC.md` があれば目的・受け入れ条件・固定要件の根拠として読む。無い場合は、現在の依頼から作業範囲と成功条件を明示して進めるか、結果を大きく変える不足だけをユーザーに確認する。
- 他のスキル名は任意の連携先である。利用中クライアントで使えて必要なら呼び出し、使えなければこのスキル内で必要な確認を行う。
- ユーザーが明示的に依頼しない限り、`git add`、`git commit`、`git push`、デプロイ、破壊的操作を実行しない。実行時はクライアントの承認・安全規則に従う。
- 固定のタスク管理方法、ホームディレクトリ、ポート、モデル、コンテナ、サービス名を仮定しない。環境依存情報は実際の設定と観測結果で確認する。

外部から観察できる振る舞いを変えずに、内部の構造だけを改善する。

## 進め方

1. 対象コードの構造、依存関係、テストの有無を確認し、何が問題かを特定する。
2. 既存テストを実行し、通ることを確認する。テストが無い、または足りない場合は、構造を変える前に、現在の振る舞いをそのまま固定するテストを書く。
3. 計画を立てる。何を、どの順で、どう変えるか。各ステップは小さく、単独で検証できる大きさにする。この変更で具体的に何が良くなるのか（次の機能追加が楽になる、不具合の原因が追いやすくなる、など）を言葉にする。
4. 計画をユーザーに提示し、承認を得る。
5. 1ステップずつ変更し、そのたびにテストを実行する。落ちたら、そのステップを戻して原因を調べる。
6. 完了を報告する。何を、なぜ、どう変えたか。テストが通り続けていること。変更前後の構造の違い。

## 判断の基準

- 構造の改善と、振る舞いの変更（機能追加、不具合修正）を1つの変更に混ぜない。途中で不具合を見つけたら、直さずに報告する。
- 「きれいにする」を目的にしない。具体的な改善を説明できない変更はしない。
- たまたま同じ形のコードを、それだけの理由で共通化しない。将来別々に変わるものは分けたままにする。
- 今使われていない抽象化、インターフェース、層を足さない。
- 書き直した方が早く安全な場合は、そう提案する。
- 公開インターフェース、保存データの形式、設定の名前は振る舞いの一部である。変えるなら固定要件と利用元を確認し、ユーザーに確認する。
