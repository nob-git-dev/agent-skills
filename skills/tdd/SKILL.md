# テスト駆動の実装

受け入れ条件を、失敗を確認したテストと必要十分な変更へ変える。完了の根拠は「通ったテストと実行結果」であり、自己申告ではない。

## 実行ルール

- 現在のユーザー依頼、利用中クライアントの権限規則、リポジトリ内の指示を優先する。
- ユーザーが明示的に依頼しない限り、`git add`、`git commit`、`git push`、デプロイ、外部書き込み、破壊的操作を実行しない。
- 環境依存の情報（ポート、モデル、コンテナ、サービス名）は仮定せず、実際の設定と観測で確認する。
- 固定要件、既存の必須テスト、公開契約を実装の都合で変えない。変更が必要なら実装を止め、理由と影響を報告する。
- 未コミットの変更はユーザーの作業として保全する。

## 1. 何を正典にするか

1. `TEST_CONTRACT.md`（または `SPEC.md` 内の Test Contract）がある案件は、それを正典にする。Proof Obligation を確認項目として使い、関連するものはまとめて進めてよい。
2. Test Contract が無い軽量・標準の変更は、`SPEC.md` の受け入れ条件と検証方法、または現在の依頼から直接進める。Test Contract をここで作らない。
3. Test Contract が無い高リスク変更（認証、認可、金銭、個人情報、永続データ、移行、破壊操作、外部副作用、本番、高負荷）は、本番コードに着手する前に `test-contract` の工程を踏む。

受け入れ条件が矛盾する、期待結果が観測できない、結果を変える情報が欠けている場合は、推測で補わずユーザーに確認する。

## 2. 進め方

1. `SPEC.md` を読み、目的、受け入れ条件、固定要件、スコープ外を確認する。
2. 既存のテスト規約、テスト環境、対象コードの作りを確認する。関連するコードは必要なだけ読む。
3. 受け入れ条件を、まとめて実装・検証できる振る舞いの単位に分ける。条件1つごとに機械的に刻まない。
4. 単位ごとに次を回す。
   - 受け入れ条件に直接対応するテストを書き、実行して、対象の振る舞いが未実装または壊れているために失敗することを確認する。fixture の誤りや環境不備で落ちているなら、製品コードを触らずにテスト側を直す。
   - 既に通る場合は、そのテストが条件を本当に確かめているかを見る。確かめているなら不要な変更をしない。
   - 必要十分な変更でテストを通す。既存テスト、期待結果、fixture を都合よく弱めない。
   - 今回の変更が生んだ重複や読みにくさは、テストが通る状態で小さく直す。
   - 対象テストと必要な回帰テストを実行する。
5. 結合、E2E、ブラウザ、実機、負荷、耐久など重い検証は、単位ごとには回さず、まとまった時点と最後に実行する。

## 3. 範囲と確認

- 変更は依頼の範囲に留める。範囲外で気づいた不具合や設計上の懸念は、直さずに報告へ書く。気づいたことを黙って捨てない。
- 結果を変える解釈の分かれ目に当たったら、独断で進めずユーザーに確認する。どちらでも結果が変わらない軽微な選択は、選んだ内容と理由を控えておき、最後にまとめて示す。
- 固定要件を満たせないと分かったら、代替へ黙って切り替えず、止めて報告する。

## 4. テスト環境の分離

- テスト用の資源が本番から分離されていることを、名前ではなく設定と観測で確認する。
- 課金、通知、永続データ、権限境界、稼働中サービスに触れるテストは、モック、sandbox、専用環境、明示承認のいずれかを使う。
- テストの実行自体が破壊的または稼働中サービスに影響する場合は、実行せず、必要な承認と安全条件を示す。

## 5. 完了の判定

受け入れ条件ごとに、実行したコマンドと結果を根拠として判定を示す。

```markdown
| 受け入れ条件 | 根拠（テスト名・コマンド・結果） | 判定 |
|---|---|---|
| 無効な拡張子は 422 | test_invalid_ext, exit 0 | PASS |
| 処理を30秒で中断できる | 未実行（実機が必要） | UNVERIFIED |
```

- `PASS` は実際に実行して確認したものだけに付ける。設計上は満たすはずでも、確認していなければ `UNVERIFIED` と書く。
- 全体のテストが通っていても、その条件を確かめるテストが無ければ `UNVERIFIED` である。
- 必要な重い検証を実行できなかった条件は `PASS` にしない。
- 条件を満たした時点で、その条件への追加変更を止める。

## アンチパターン

- 本番コードを先に書き、実装に合わせてテストを後付けする
- 失敗を確認せず、テストが条件を確かめていると仮定する
- テストを通すために、既存テストや期待結果を弱める
- 受け入れ条件を細かく刻み、項目の消化を進捗とみなす
- 範囲外で気づいた問題を、報告せずに直す、または報告せずに捨てる
- 重い検証を速度やトークンのために省いたまま完了とする
- コマンドと結果のない「テスト済み」を根拠にする
