# 概念の階段

新しい概念、仕組み、フレームワーク、判断基準を説明するときに使う。
定義から始めず、読者がその概念を必要とする状態を作ってから名前を与える。

## 8段階

### 1. 既知の地点

読者がすでに理解できる現象、経験、事実から始める。
前提知識を要求しすぎない。

### 2. 違和感または矛盾

期待と現実が一致しない点を一つ示す。
複数の問題を同時に持ち込まず、中心的な矛盾を選ぶ。

### 3. 既存説明の限界

一般的な説明や従来のやり方が、どこまでは有効で、どこから説明できないかを示す。
既存の考えを全否定せず、適用限界を特定する。

### 4. 原因仮説

複数の観察を説明できる共通要因を置く。
事実ではなく仮説である場合、その確度を明示する。

### 5. 命名と定義

必要性が理解された段階で、概念に短い名前を付ける。
定義を一文で書き、似た概念との違いを一つ示す。
新語を増やさず、同じ名前を一貫して使う。

### 6. 説明力の確認

概念を使うと、先ほどの矛盾がどう説明できるかを示す。
一つは単純な例、もう一つは実際の利用場面で確かめる。

### 7. 適用と境界

政策、事業、プロジェクト、個人行動など、必要なレベルへ適用する。
適用できない条件、例外、追加検証が必要な点も示す。

### 8. 行動への接続

概念を理解すると、何を変えて判断・実行できるのかを示す。
結論を抽象論で終わらせない。

## 各節の契約

各節を次の5要素で設計する。

1. 前節から受け取る前提
2. この節で答える問い
3. 答えを支える事実、比較、または例
4. 一文の暫定結論
5. 次節で必要になる問い

一つの節で進める概念は一段だけにする。

## 骨格例

- 観察: AIとの議論が増えるほど、共有文書が分かりにくくなる。
- 矛盾: 情報量は増えているのに、第三者の理解は進まない。
- 既存説明の限界: 単純な要約では、判断理由や未解決事項が消える。
- 原因仮説: 会話の順序と、読者が理解する順序は異なる。
- 概念: 読者の疑問を基準に情報を並べ直す「読者質問構造」を使う。
- 確認: 同じ対話を、背景→問題→判断→根拠→次の行動へ再配置する。
- 境界: 発言の意図や不足する事実は推測で埋めない。
- 行動: 文書化の前に、読者の疑問を列挙する。

## 失敗パターン

- 概念名だけを先に掲げ、必要性を示さない
- 一段の中で複数の新語を定義する
- 例を増やすだけで、共通原理を抽出しない
- 前節と関係のない話題を追加する
- 数字を示すが、その意味を説明しない
- 仮説を証明済みの結論として扱う
- 概念の説明だけで終わり、利用場面へ接続しない

## 短い文書での圧縮

短文では段階を削除せず、次の4ブロックへ統合する。

1. 現象と矛盾
2. 既存説明の限界と原因仮説
3. 概念の定義と説明力
4. 適用、境界、行動
